## 0. 一分钟摘要

我独立设计并开发了一个 AI 个人上下文系统：**小鹈鹕 TinyPelican**。

它的出发点是：**AI 之所以不够懂用户，不是模型不够强，而是缺少持续、统一、跨场景的个人上下文。**

今天，一个人的信息散落在微信、QQ、飞书、邮件里，真实活动散落在现实和记忆里，任务和日程分散在不同 App 中。通用 AI 每次对话都从零开始，没有长期记忆，也无法主动行动。

小鹈鹕的核心特点是 **主动智能**：

```text
多途径聊天记录 + AI 硬件采集的现实活动
                ↓
      统一记录与管理（个人上下文层）
                ↓
自动识别聊天中的意图、承诺、时间与关系信号
                ↓
主动生成「待确认任务 / 提醒 / 日程」
                ↓
用户确认 / 修改 / 忽略
                ↓
系统在正确时机主动提醒、主动推进
                ↓
用户反馈回流 → 记忆更准
                ↓
              数据飞轮
```

目前，MVP 已经跑通 **自动意图识别 → 主动生成待确认任务 → 用户确认 → 主动提醒** 的完整闭环，并已开源。

> **核心差异：不是用户问 AI，而是 AI 主动发现、主动生成、主动提醒。**

## 1. 拟解决的问题

### 1.1 问题背景

传统个人 CRM（以 Monica 为代表）验证了一个真实需求：**人需要记住重要的人和事**。但它有一个致命缺陷：

> **所有数据都需要用户手动录入。**

联系人要手动填，活动要手动记，日记要手动写，提醒要手动设。工具越强大，维护成本越高，最终被用户放弃。

### 1.2 核心痛点

用户真正需要的，不是「一个更漂亮的通讯录」，而是：

> **不用主动想，也能被提醒；不用手动整理，也能记住；不用反复交代，AI 也能推进。**

### 1.3 我的产品假设

如果把输入成本降到接近零，AI 就能持续完成三件事：

1. **自动记录**：聊天和现实活动自动进入统一记忆；
2. **自动理解**：AI 抽取人物、承诺、偏好、边界和时间；
3. **主动行动**：在正确时机提醒、建议、推进工作，而不是等人提问。

### 1.4 一个真实的产品决策：微信约束与多平台接入

在设计输入通路时，我遇到了一个典型的平台生态难题：

- **个人微信是用户使用频率最高的聊天平台，但微信生态不开放聊天记录导出 API**；
- 通过 hook、逆向、数据库解包获取聊天记录，存在明显的合规与封号风险，不能作为长期产品方案；
- 因此我选择了 **「复制聊天 → 剪贴板自动识别」的半自动路径**：用户只需要复制，系统自动解析、去重、归档。

这不是产品理想态，而是在平台生态约束下，优先保证合规与用户信任的最优解。

同时，我在架构上做了统一通道抽象：

| 平台 | 开放程度 | 接入方式 |
|---|---|---|
| 个人微信 | 无公开导出 API | 剪贴板半自动 + 实验性 bot 通道 |
| QQ | 有结构化导出路径 | 直接导入结构化聊天记录 |
| 飞书 | 有开放 API / 导出能力 | 自动同步结构化消息 |
| 钉钉 | 有开放 API / 导出能力 | 自动同步结构化消息 |
| 邮件 / 日历 | 标准协议 | 直接接入 |
| AI 眼镜 / 相机 / 手表 | 取决于厂商开放度 | 统一活动接入层（规划） |

**对开放平台走自动导入，对封闭平台走剪贴板半自动，对所有来源统一归一成同一种记忆格式。**

这体现了我在平台生态、合规风险、用户体验和开发成本之间做取舍的产品能力，也为未来多平台扩展预留了架构空间。

## 2. AI 的介入方式

### 2.1 总体架构

```text
多途径聊天记录（微信/QQ/飞书/钉钉/邮件）
+ AI 硬件现实活动（眼镜/相机/手表）
                    ↓
         统一记录与管理（个人上下文层）
                    ↓
   AI 理解：人物、承诺、偏好、边界、时间
                    ↓
       结构化知识库 / 意图库 / 时间线
                    ↓
      主动生成待确认任务 / 提醒 / 日程
                    ↓
       用户确认 → 主动提醒 / 主动推进
                    ↓
       反馈回流 → 记忆更准 → 数据飞轮
```

设计原则：

- **AI 负责**：理解、抽取、建议、起草；
- **系统负责**：校验、落库、调度、审计；
- **人负责**：确认、修正、最终决策。

AI 主动，但永远保留人的控制权。这是整个产品的安全底线。

### 2.2 主动智能闭环：自动意图识别 → 待确认任务 → 主动提醒

这是我产品设计中最核心的亮点，也是最能体现「主动智能」的部分。

#### 第一步：自动识别聊天中的意图

当新聊天记录被归档后，系统自动触发意图识别，而不是等待用户输入指令。AI 会从对话中抽取：

- 需要用户做的事情（todo）；
- 需要在某个时间提醒的事（reminder）；
- 有明确开始/结束时间的活动（schedule）；
- 承诺、委托、等待回复、截止时间等关系信号。

证据：`core/engine/intent-runner.js`、`core/engine/prompts/intent.js`。

#### 第二步：主动生成「待确认任务」

AI 不会直接把识别结果变成正式任务或提醒，而是先进入「待确认」队列。每条待确认意图都包含：

- 类型：todo / reminder / schedule；
- 摘要与原文摘录；
- 时间解析结果；
- 涉及的人；
- 置信度；
- 判定理由；
- 来源消息与时间。

用户可以一键确认、修改或忽略。这样既保留了 AI 的主动性，又避免了误判直接执行。

证据：`core/memory/stores/intents.js`、Dashboard 的「待确认行动」页面。

#### 第三步：用户确认后，主动提醒

用户确认后，意图才转成正式任务、提醒或日程，并由系统在正确的时机主动触达用户：

- DDL 提前提醒；
- 日程开始前提醒；
- 周期性提醒；
- 免打扰时段自动避让；
- 提醒文案按需生成，平时 0 token，只有到时间点才调用模型；
- 支持微信推送与 Bark，后续可扩展更多通道。

证据：`core/remind/scheduler.js`、`core/remind/runner.js`、`core/notify.js`。

#### 第四步：反馈回流，让主动越来越准

用户的每一次确认、修改、忽略，都是隐式反馈：

| 用户行为 | 反馈含义 |
|---|---|
| 确认 | 该类型意图可信 |
| 修改 | 模型抽取有偏差 |
| 忽略 | 可能是误判或不需要 |

这些反馈会用于后续 Prompt 优化和规则调整，让主动智能越来越懂用户。

> **主动智能的设计边界：** AI 负责「主动想到」；系统负责「主动调度」；人负责「最终确认」。  
> 这就是「主动智能」与「自动驾驶式失控」之间的区别。

### 2.3 Prompt 工程与版本演进

我为核心任务分别设计了独立 Prompt，并以「意图识别」为例完成了多轮迭代。源文件位于 `core/engine/prompts/intent.js`。

#### v1：单条消息直接抽取

- 做法：把单条聊天丢给模型，问「有没有任务」；
- 问题：缺少上下文，同一件事被反复识别，时间表达歧义严重。

#### v2：按批次 + 时间上下文抽取

- 做法：按联系人、按批次输入，附带消息时间戳和当前时间；
- 改进：能处理「下周一」「后天」等相对时间；
- 问题：模型会编造不存在的截止时间，JSON 格式不稳定。

#### v3：强约束结构化输出

- 做法：要求只输出 `NO_TASK` 或严格 JSON 数组，定义完整字段：`type / summary / detail / deadline / endAt / execution / recurrence / people / priority / confidence / reason`；
- 改进：输出可程序化解析，可直接落库；
- 问题：模型倾向于把闲聊也识别成任务。

#### v4：规则前置 + 置信度 + 人机确认

- 做法：在 Prompt 中写入明确判断规则（未来时间、委托、等待回复必须识别；纯闲聊、过去事实、已完成陈述必须输出 `NO_TASK`），并要求模型给出 `confidence` 和 `reason`；
- 系统侧：解析后不直接执行，先进入「待确认」队列；
- 结果：误识别显著减少，用户可以用确认 / 忽略 / 修正进行反馈。

> **关键设计取舍：** 把「理解」和「执行」解耦。模型只负责语义理解和结构化；系统负责时机判断和校验；人负责最终确认。这样能显著降低幻觉造成的不可逆风险，同时保留主动智能。

### 2.4 从模型输出到结构化系统

模型输出不会直接变成操作，而是经过完整的系统校验：

| 环节 | 说明 |
|---|---|
| 类型归一化 | `todo / reminder / schedule` |
| 执行方式归一化 | `manual / system / dsh` |
| 时间解析 | 结合消息时间戳解析相对时间 |
| 去重 | 同一联系人、同一时间、同一内容不重复创建 |
| 状态管理 | `pending_confirm → confirmed → done / ignored` |
| 执行边界 | 只有用户确认后，才进入正式任务列表或提醒调度 |

证据：`core/engine/intent-runner.js`。

### 2.5 记忆库与知识库建设

我设计了两类长期记忆：

#### ① 联系人档案

- 一人一档：关系、近况、偏好、重要承诺、敏感话题、最近互动；
- 持续更新：从聊天记录中自动抽取，不覆盖用户手写内容；
- 原则：只写有依据的推断，拿不准标记「待观察」，绝不臆测。

#### ② 聊天与意图时间线

- 按人物、按时间检索；
- 每条意图保留来源消息、置信度、确认状态；
- 为 AI 的回复建议和提醒提供可追溯的上下文。

> 这套「结构化条目 + 来源追溯 + 分层优先级」的方法，是我在知识库建设上的核心实践。

### 2.6 Agent 工作流：可审计、可复盘

我使用 DSH Agent 执行用户确认后的任务，而不是让模型直接操作数据库：

- 任务写入队列，Agent Worker 拉取执行；
- 事件流记录 `assistant/chunk`、`tool/call`、`tool/result`、`step/start`、`step/end`；
- 前端可逐步展示 AI 的思考与工具调用；
- 任务失败、超时、重启都有状态管理。

> **价值：可解释、可复盘、可管控。**  
> 每一条 AI 输出都可以追溯到具体步骤和证据。

### 2.7 幻觉识别与安全边界

我建立了一套「AI 输出安全边界」方法：

1. **来源约束**：要求模型输出必须引用知识库条目或原文；
2. **自动核验**：用规则或二次模型逐条比对来源，标记「无来源 / 过度推断 / 与来源矛盾」；
3. **人工抽检**：建立失败案例库，统计错误类型，持续优化；
4. **人在回路**：不确定的回答不开放，不可逆操作必须确认；
5. **边界声明**：在产品最前面写清能力边界，避免用户误用。

这套方法可以用于任何需要高质量 AI 输出的场景。

### 2.8 数据清洗与流程自动化

我完成过多类数据清洗与自动化实践：

- 聊天记录解析：按「昵称 + 时间 + 内容」切分，处理表情、图片、语音占位符；
- 消息去重：按人物 + 时间 + 类型 + 内容去重；
- 语音回填：按顺序将转写文本回填到对应语音消息；
- 通知推送：微信 + Bark 双通道，支持免打扰；
- 定时任务：提醒调度、关系维护检查、Agent 队列消费；
- 多通道适配：为 QQ、飞书、钉钉、邮件等结构化导入预留统一接口。

### 2.9 产品测试与迭代

- 建立了覆盖核心链路的测试套件，覆盖聊天解析、意图生成、提醒规则、日程解析、Agent 队列、事件流、回复建议、语音回填、登录流程等；
- 用人工流程测试模拟真实用户操作，发现问题后回写测试或调整 Prompt；
- 每个 Prompt 版本都保留迭代逻辑，能够说明「为什么改、改了什么、解决了什么问题」。

## 4. 当前阶段与下一步迭代方向

当前项目处于 **MVP 阶段**：核心闭环已经跑通，并已开源。下一步迭代方向非常清晰：

1. **多平台自动导入**：QQ、飞书、钉钉等结构化导入通道持续推进，逐步实现「开放平台自动同步」；
2. **更多的上下文来源**：接入 AI 眼镜、AI 相机、AI 手表等硬件，把现实活动导入同一个记忆系统；
3. **主动智能增强**：更准的意图识别、更智能的提醒时机、更丰富的主动建议；
4. **检索升级**：在结构化检索基础上引入向量检索与重排序，提升长期记忆的召回质量；
5. **Prompt 回归测试**：建立可量化的 Prompt 评估集，让版本迭代从人工判断升级为数据驱动；
6. **工程稳定性**：完善 CI 门禁与测试稳定性，为后续多人协作和平台化打基础；
7. **真实用户验证**：用种子用户验证激活率、采纳率与留存，推动产品从技术可行走向价值验证。
